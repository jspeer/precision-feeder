## Premise

Every control channel (web app, BLE, Home Assistant, MQTT) grew its own reach one feature at a time. 2.1 made it
visible: MQTT, added beside the native API, exposed everything Home Assistant sees, guard limits, calibration and
pins included, behind nothing but the broker's login; and the hand edit of the 24 h count, which AGENTS.md allows in
Home Assistant only, is also on the web app (DESIGN.md section 14, items 24 and 25).

2.2.0 sorts what the feeder offers into three kinds, and gives each channel a reach that matches how well it knows
who is talking. The owner's framing (2026-10-22): the **device** is a fish feeder (scheduling, actuation); calibration,
keys, Wi-Fi, the drive and so on are functions of its **components**.

## The three kinds

| Kind | What it holds |
|---|---|
| **Operate** (the feeder) | feed now (one, or N portions), tray reload, stop, hold and cancel hold, the scheduler switch, the active profile, and status: portions remaining, tray state, next feed, last feed and its result, recent feeds, today's feeds, faults, needs food, firmware version |
| **Safety policy** (the feed guard) | daily portion cap, minimum gap between feeds, gap between portions, max portions per command, the 24 h count's hand edit |
| **Components** (the device) | calibration and recovery, servo pulse range, the disc's tuning and slot count, drive, pins, board, keys, settings password, name, Wi-Fi, access point, time zone, NTP servers, location, reload pause, refill interval, MQTT's own settings, restart, firmware, diagnostics |

The schedule's editing (profiles, events, one-shots) is Operate in substance but stays where it is today: the web app
and BLE (its records). See question Q2.

## The channels, and how each knows who is talking

| Channel | Trust | Operate | Safety policy | Components |
|---|---|---|---|---|
| Web app | the settings password (when set) on every protected change; open on the LAN otherwise | yes | yes, protected | yes, protected |
| BLE | a key, every write signed and sequenced; per device | yes | behind its switch (as today) | calibration only, behind its switch (as today) |
| Home Assistant (native API) | the API encryption key, per device | **yes (the slim set)** | **no** | **no** |
| MQTT | the broker's login: no per-message signature; every client the broker lets publish can command | **yes (the slim set)** | **behind a new switch, off by default** | **never** |

- **BLE does not change.** It is already the headless channel: everything a controller needs after setup, the safety
  policy and calibration behind the two switches (BLE Can Change Guard Limits, BLE Can Change Calibration).
- **Home Assistant is scoped down** to the slim set (below). Everything else becomes web-app only (`internal: true`
  with `web_server: include_internal: true`). An existing feeder's Home Assistant loses those entities on upgrade;
  a YAML build can keep the full set (D23).
- **MQTT gets the slim set by default**, as Home Assistant does (internal entities are never published over MQTT,
  checked in the ESPHome 2026.10.0 source). An advanced user can let MQTT change the safety policy with a new switch,
  **MQTT Can Change Guard Limits**, web-app only and protected, off by default. MQTT never reaches the components.
- **The 24 h count's hand edit** is safety policy: web app only, behind the settings password. It leaves Home
  Assistant (reversing "in Home Assistant", decision 2026-10-14) and is not added to BLE or MQTT.

## Decisions to log (when the owner confirms them)

- **D21** The three kinds and the channel table above.
- **D22** Home Assistant and MQTT see the slim set; everything else is web-app only.
- **D23** A YAML build can keep the full Home Assistant set: substitution `ha_entities: full` (default `slim`). The
  prebuilt binaries are slim. (For a feeder whose Home Assistant automations use the other entities; see Q3.)
- **D24** MQTT may change the safety policy only with **MQTT Can Change Guard Limits** on (default off; a Device flag
  bit, so no record layout changes). It does so through its own command topic (M3), not through entities.
- **D25** The 24 h count's hand edit: web app only (closes open item 25; AGENTS.md updated).
- **D26** MQTT's components rule: never (closes open item 24).

## Milestones

**M0, facts (no code).** In the ESPHome 2026.10.0 source and by validating test configs:
- `internal: true` hides an entity from the API and from MQTT discovery and state, and `include_internal` keeps it in
  the web server's REST and event stream (the 2.1 size experiment showed both on 2026.9.1).
- A substitution can drive `internal:` (`internal: ${ha_hidden}`), so D23 is one switch.
- `mqtt: on_json_message` and `mqtt.publish_json` (both present in 2026.10.0) for M3; the topic prefix in use at the
  time the subscription is made (2.1.2 sets it at boot, before the client starts).
- What the Home Assistant API does with an entity that was there and is now internal (it disappears; the HA entity
  registry keeps it as unavailable until removed by hand). Write that down for the upgrade note.
- Measure: flash and RAM of the full binary before and after (expected unchanged: ESPHome still generates the
  handlers).

**M1, entity scopes.**
- Every entity in `packages/` gets a kind (Operate, Policy, Component) and its visibility: the slim set visible,
  everything else `internal: ${ha_hidden}`. The web app needs `include_internal` (packages/web_server.yaml).
- A build without the web server would have no way to reach the internal entities: `ha_hidden` follows whether the
  web_server package is included, or the packages document that slim needs the web app (to settle in M0).
- `tests/test_consistency.py`: every entity is classified (a table in the test or a comment marker in the YAML), the
  slim set is exactly the documented list, and no Component entity is visible.
- Web app: unchanged in behaviour (it already reads every entity by name). Check `web/src/entities.js` still resolves
  everything with `include_internal`, on the mock device and the bench.

**M2, the 24 h count.** Portions Counted (24 h) becomes web-app only (internal, protected as today). AGENTS.md's
safety rule rewritten: the hand edit is allowed in the web app behind the settings password, nowhere else. DESIGN.md
section 4 and the decision of 2026-10-14 updated (D25).

**M3, MQTT and the safety policy.**
- Device flag `DEVICE_MQTT_GUARD` (0x08, default off; the record's layout and version unchanged; the flags mask
  extended; host-tested like the BLE flags). Switch **MQTT Can Change Guard Limits** in packages/mqtt.yaml: web-app
  only, protected.
- A command topic `<prefix>/feeder/policy/set` taking JSON, for example `{"daily_cap": 3, "min_gap_s": 60}`, and a
  state topic `<prefix>/feeder/policy` (retained) with the current values. Every value goes through FeederCore's
  setters (limits enforced as for every other channel). With the switch off, a command is refused and logged, and
  the state topic still reports (read-only).
- The parsing and the refusal live in FeederCore (pure, host-tested: a `PolicyCommand` from key/value pairs, the
  result per key), the adapter only moves JSON. Host tests: every key, out-of-range values, unknown keys, switch off.
- Not over MQTT, ever: the 24 h count's edit, calibration, components.

**M4, web app.** Configuration, MQTT card: the new switch, with what it allows. Keys card: the BLE switches unchanged.
A short "Who can change what" note (the channel table, in plain words) on the Configuration page or in WEB_UI.md.
Check the 66 KB budget.

**M5, docs.** DESIGN.md: a new section "Channels and scopes" (the tables above, D21 to D26), sections 7 (Home Assistant
entities, now the slim set), 9.6 (MQTT), 10 (security). SECURITY.md's "Who can do what" table. USING.md (what Home
Assistant shows). INSTALL.md and BUILDING.md (the upgrade note; `ha_entities: full`). PROTOCOL.md unchanged (BLE
unchanged). CHANGELOG.md 2.2.0 with the upgrade note in its first lines. AGENTS.md: the scope rule ("a new entity is
classified; Components are never visible to Home Assistant or MQTT").

**M6, bench.** On both rigs, prebuilt `full` and `no-ble`:
- Home Assistant (adoption on the native API): exactly the slim set; an upgraded feeder's removed entities shown as
  unavailable, nothing else broken; the slim set controls the feeder.
- MQTT: discovery is exactly the slim set; the policy topic refused with the switch off, applied with it on (and
  clamped to the limits); its state topic.
- BLE: selftest 13/13; the permission switches as before.
- Web app: every page and card works with the internal entities (Configuration, Maintenance, the disc wizard,
  Diagnostics' entity list).
- A YAML build with `ha_entities: full`: the full set in Home Assistant, as 2.1.

## Questions for the owner

- **Q1** The slim set: keep Feed Selected Portions with Manual Portions (N portions per command)? Active Profile?
  Anything to add (Portions Fed Today, Runway, Hold, Tray Empty On)?
- **Q2** Schedule editing in Home Assistant: today the schedule editor entities (Edit Profile, Edit Event, Event Time,
  ...) are in Home Assistant. Scoped down they go web-app only (BLE keeps its records). Agreed?
- **Q3** Your production feeder: do any of its Home Assistant automations or dashboards use entities outside the slim
  set? If yes, its YAML build sets `ha_entities: full` (D23), or we add those to the slim set.
- **Q4** BLE calibration: it stays behind its switch, as today, even though calibration is a component function in
  the new model. Keep it (headless recalibration from a controller), or take it off BLE?
- **Q5** The MQTT policy topic's format: JSON on `<prefix>/feeder/policy/set` as above, or one plain topic per value
  (`<prefix>/feeder/policy/daily_cap/set`, payload `3`)? JSON is one message for several values; plain topics are
  easier from a PLC.
