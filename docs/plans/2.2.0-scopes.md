## Premise

Every control channel (web app, BLE, Home Assistant, MQTT) grew its own reach one feature at a time. 2.1 made it
visible: MQTT, added beside the native API, exposed everything Home Assistant sees, guard limits, calibration and
pins included, behind nothing but the broker's login; and the hand edit of the 24 h count, which AGENTS.md allows in
Home Assistant only, is also on the web app (DESIGN.md section 14, items 24 and 25).

2.2.0 sorts what the feeder offers into three kinds, and gives each channel a reach that matches how well it knows
who is talking. The owner's framing (2026-10-22): the **device** is a fish feeder (scheduling, actuation); calibration,
keys, Wi-Fi, the drive and so on are functions of its **components**.

## The three kinds

| Kind | What it holds |
|---|---|
| **Operate** (the feeder) | feed now (one, or N portions), tray reload, stop, hold and cancel hold, the scheduler switch, the active profile, and status: portions remaining, tray state, next feed, last feed and its result, recent feeds, today's feeds, faults, needs food, firmware version |
| **Safety policy** (the feed guard) | daily portion cap, minimum gap between feeds, gap between portions, max portions per command, the 24 h count's hand edit |
| **Components** (the device) | calibration and recovery, servo pulse range, the disc's tuning and slot count, drive, pins, board, keys, settings password, name, Wi-Fi, access point, time zone, NTP servers, location, reload pause, refill interval, MQTT's own settings, restart, firmware, diagnostics |

The schedule's editing (profiles, events, one-shots) is Operate, but it is not for Home Assistant (owner, Q2: "HASS
has no business editing the schedules. If you want that functionality, re-adopt under MQTT"). It is on the web app,
BLE (its records) and MQTT (M3).

## The channels, and how each knows who is talking

| Channel | Trust | Operate | Safety policy | Components |
|---|---|---|---|---|
| Web app | the settings password (when set) on every protected change; open on the LAN otherwise | yes | yes, protected | yes, protected |
| BLE | a key, every write signed and sequenced; per device | yes | behind its switch (as today) | calibration only, behind its switch (as today) |
| Home Assistant (native API) | the API encryption key, per device | **the slim set (no schedule editing)** | **no** | **no** |
| MQTT | the broker's login: no per-message signature; every client the broker lets publish can command | **the slim set, plus schedule editing on its own topics** | **behind a new switch, off by default** | **never** |

- **BLE does not change.** It is the headless channel: everything a controller needs after setup, the safety policy
  and calibration behind the two switches (BLE Can Change Guard Limits, BLE Can Change Calibration). Pins, drive, keys
  and network stay off BLE: they are set in the web app or in the YAML. A fully headless build leaves the web app
  out, sets its pins in the YAML and is run over BLE (owner, Q4).
- **Home Assistant is scoped down** to the slim set (below). Everything else becomes web-app only (`internal: true`
  with `web_server: include_internal: true`). An existing feeder's Home Assistant loses those entities on upgrade:
  remove the stale ones, or delete the device and adopt it again (owner, Q3: no automation of the production feeder
  uses them, so no "full set" build option).
- **MQTT is the advanced channel**: the slim set's entities (with Home Assistant discovery), plus its own plain topics
  (M3) for the schedule and, behind a new switch, the safety policy. Internal entities are never published over
  MQTT (checked in the ESPHome 2026.10.0 source), so those topics are ours, not entities. The switch, **MQTT Can
  Change Guard Limits**, is web-app only and protected, off by default. MQTT never reaches the components.
- **The 24 h count's hand edit** is safety policy: web app only, behind the settings password. It leaves Home
  Assistant (reversing "in Home Assistant", decision 2026-10-14) and is not added to BLE or MQTT.

## Milestones

**M0, facts (no code).** In the ESPHome 2026.10.0 source and by validating test configs:
- `internal: true` hides an entity from the API and from MQTT discovery and state, and `include_internal` keeps it in
  the web server's REST and event stream (the 2.1 size experiment showed both on 2026.9.1).
- `mqtt: on_message` with a wildcard (`<prefix>/feeder/+/set`, or one subscription per topic) and `mqtt.publish`
  for M3; whether a wildcard subscription is allowed and what it costs; the topic prefix in use when the subscription
  is made (2.1.2 sets it at boot, before the client starts); retained state topics.
- What the Home Assistant API does with an entity that was there and is now internal (it disappears; the HA entity
  registry keeps it as unavailable until removed by hand). Write that down for the upgrade note.
- Measure: flash and RAM of the full binary before and after (expected unchanged: ESPHome still generates the
  handlers).

**M0 results (2026-10-22, ESPHome 2026.10.0 source; the disc on 2.1.2 for the web app):**
- **`internal: true` hides an entity from the native API**: its list (`ComponentIterator`, `include_internal` false
  for the API) and its state updates (`APIServer::on_*_update` returns for internal entities). **And from MQTT**:
  `MQTTComponent::call_setup()` never registers an internal one (no discovery, no state, no command). **Trap:** an
  entity with an explicit MQTT `state_topic` or `command_topic` counts as not internal for MQTT
  (`compute_is_internal_`), so internal entities must never get custom topics. M1's consistency test checks it.
- **`web_server: include_internal: true`** keeps them in the web server's REST and event stream
  (`ComponentIterator::begin(include_internal_)`, and every handler's `!include_internal_ && is_internal()` check).
  Shown on hardware already: 2.1's MQTT settings are internal, and the web app reads and writes them.
- **The settings password still guards internal entities:** our guard matches the request's URL against the
  protected names (`PrecisionFeeder::is_protected`), whatever the entity's visibility.
- **Our own MQTT topics are subscribed at run time, not in YAML:** a YAML `on_message` topic is fixed at build time,
  but the topic prefix is the device's (saved, or its name, set at boot since 2.1.2). `MQTTClientComponent::subscribe()`
  works before a connection, keeps the subscription and resubscribes after every reconnect; `+` and `#` wildcards are
  matched (`topic_match`). So one subscription, `<prefix>/feeder/#`, routed in our code. `publish(topic, payload, qos,
  retain)` for the state topics. Subscribe in a component whose setup runs after the boot lambda that sets the prefix
  (priority below 600: AFTER_WIFI).
- **Messages arrive on the main loop** (the ESP-IDF backend queues them from its task: `mqtt_event_queue_`), so calling
  FeederCore from them is safe. The queue drops events when its pool is full (counted, logged): docs/MQTT.md says to
  send values one at a time.
- **No connect hook to share:** the client has one `set_on_connect` slot, which the YAML `on_connect` trigger uses.
  Ours watches `is_connected()` turning true in its loop and republishes the retained state topics then.
- **Home Assistant and an entity that becomes internal:** not stated in the HA or ESPHome docs; community reports
  said it stays in HA's registry as unavailable. **Checked in M6:** the ESPHome integration removes it by itself
  (124 entities on 2.1.2, 20 right after the upgrade to 2.2.0).
- **Size:** making 104 entities internal moved the 2.1 experiment's full binary by under 1 KB (ESPHome still
  generates their handlers). Measured again in M1 on 2026.10.0.
- **The MQTT glue compiles out with MQTT:** it goes in its own component (`components/precision_feeder_mqtt`), included
  only by packages/mqtt.yaml, with the routing in a pure, host-tested class beside FeederCore.

**M1, entity scopes.**

**M3, MQTT's own topics: the schedule and the safety policy.** Plain topics, one value each (Q5), under
`<prefix>/feeder/`: a retained state topic per value, and `.../set` to change it. A refused or out-of-range set is
logged and its state topic republished unchanged, so a client always reads what is in force. Every value goes through
FeederCore's setters, as for every other channel.
- **Schedule** (always allowed, like the schedule over BLE):
  - `schedule/<A|B|C>/event/<1-4>/{enabled,anchor,time,portions,days}`: an event's fields (time `HH:MM` for a clock
    event, signed minutes for sunrise or sunset; days `mon,tue,...` or `all`); portions 1 to the capacity.
  - `schedule/<A|B|C>/{every_n_days,fast_days}` and `schedule/<A|B|C>/restart_cycle` (command only).
  - `oneshot/add` (`YYYY-MM-DD HH:MM PORTIONS`), `oneshot/clear`, and a retained `oneshot/list`.
  - The active profile and the scheduler switch are entities already (the slim set).
- **Safety policy**, applied only with **MQTT Can Change Guard Limits** on (Device flag `DEVICE_MQTT_GUARD`, 0x08,
  default off; the record's layout and version unchanged; host-tested like the BLE flags; the switch in
  packages/mqtt.yaml, web-app only and protected): `policy/{daily_cap,min_gap_s,portion_gap_s,max_portions_cmd}`.
  With the switch off a set is refused; the state topics still report.
- The topic routing and value parsing live outside ESPHome, pure and host-tested (a small `MqttTopics` beside
  FeederCore: topic and payload in, a call on the core and the topics to republish out), so the adapter only
  subscribes and publishes. Host tests: every topic, bad payloads, out-of-range values, the switch off, a profile
  or event out of range, the republish after a refusal.
- Not over MQTT, ever: the 24 h count's edit, calibration, components.
- Cost: measure in M0 (one wildcard subscription and a handful of publishes; expected small).
