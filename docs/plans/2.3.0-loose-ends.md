Status: **M0 to M6 done (2026-10-22), M6 in part (docs/BENCH.md): forget Wi-Fi and the BLE key clear still need the owner at the rig.** Not merged, not tagged. Branch `release/2.3.0-loose-ends`, from main at 2.2.0. Nothing is built

## Premise

2.2.0 has almost everything the feeder was meant to have: two drives in one firmware, every setting on the device,
MQTT and the full web app. The full build is at 88.7% of the 1.8 MB app partition (1,628,155 bytes, measured
after M1), so about 200 KB is free: enough for this plan, which measures each step. The owner
decided not to leave ESPHome (2026-10-22; the 3.0 "native" idea is shelved, its questions in its own session).

What is left are three things that are common practice for a device you set up in a browser, one decision on MQTT,
and the bench:

1. **Clear the BLE key** from the web app, as the Home Assistant key already can be.
2. **Forget the Wi-Fi network** in a build that has none in its YAML (the prebuilt binaries): the network set on the
   device is the only one it has, and there is no way to remove it short of erasing the board.
3. **A Wi-Fi scan with a dropdown** when choosing a network, keeping the typed name for hidden networks.
4. **Protected settings are read-only over MQTT** (item 24): the guard's limits too.

### M0 Facts from ESPHome 2026.10.0 (no code)

Read the ESPHome source the project pins (`esphome/components/wifi`, `captive_portal`, `esp32/preferences`) and answer:

1. **Forgetting the network.** With no network in the YAML, `WiFiComponent::start()` keeps the saved one under a
   fixed preference hash (88491487). Does erasing that slot (an NVS key erase) bring the feeder back exactly as after a
   fresh flash, with its setup access point and Improv? Or does saving an empty record do the same, given that
   `setup()` loads it and calls `set_sta()` with an empty SSID? Which is the supported path, and does it need a restart?
2. **Scanning on the setup access point.** The captive portal serves scan results (`/config.json`) while the access
   point is up. Can the web app (the setup wizard on the access point) read them, and does ESPHome keep them
   (`request_wifi_scan_results`, `set_keep_scan_results`)?
3. **Scanning while connected.** Can a scan run while connected to a network without dropping it: ESPHome's
   `start_scanning()`, or ESP-IDF's `esp_wifi_scan_start()` directly, and does ESPHome's event handler then leave its
   own state alone? If neither is safe, the dropdown is offered on the access point only and Configuration keeps the
   typed name (D31).
4. **Flash** of each answer (the build has room; measure anyway).

**M0 results (2026-10-22, ESPHome 2026.10.0, read from its source):**

1. **Forgetting the network: erase one NVS key, then restart.**
   - `WiFiComponent::start()` (`wifi_component.cpp:693`) opens its saved-network record under
     `has_sta() ? App.get_config_version_hash() : 88491487`. `has_sta()` is evaluated before the saved record is
     loaded, so in a build with no network in its YAML the record is always under the fixed hash **88491487**.
   - On ESP32 a preference is an NVS blob in namespace **`esphome`**, its key the hash as a decimal string
     (`esp32/preferences.cpp`: `make_backend_` sets `key = type`; `load`/`sync` use `uint32_to_str(key)`). So the
     network is NVS key `"88491487"`.
   - An empty record is **not** the same as none: `start()` loads it and calls `set_sta()` with an empty SSID, and
     `has_sta()` is then true (`wifi_component.cpp:706-716`), so ESPHome would try to join a network with no name.
     The key has to be erased: `nvs_open("esphome")`, `nvs_erase_key("88491487")`, `nvs_commit()`. ESPHome has no erase
     for one preference (`ESPPreferences` has only a whole-store `reset()`).
   - After a restart with no record, `start()` takes the access-point path (`wifi_component.cpp:762-776`): the setup
     access point, the captive portal, and Improv, exactly as after a fresh flash. Our builds use no `provisioning:`
     window, so the access point does not close by itself. `save_wifi_sta()` syncs at once, so no save of that key is
     ever pending when we erase it. `fast_connect` is off in our builds, so its own record (hash + 1) is not used.
   - The fixed hash is ESPHome's, not ours: M3 adds a check (`tests/test_consistency.py`, when ESPHome is installed)
     that `wifi_component.cpp` still uses 88491487, so an ESPHome upgrade that changes it fails the checks rather than
     the feeder.
2. **Scanning on the setup access point: yes.** With no network, `start()` calls `start_scanning()` alongside the
   access point unless `WIFI_AP_EXCLUSIVE`, which ESPHome defines only for the LN882H chip (`wifi/__init__.py:683`;
   `wifi_component.cpp:386-388`). While the captive portal is active ESPHome keeps the full results
   (`needs_full_scan_results_()`, `wifi_component.cpp:487-491`), and the portal serves them at `/config.json` under a
   `ScanResultsLock` (`captive_portal.cpp:40-56`).
3. **Scanning while connected: yes, with ESP-IDF's scan, not ESPHome's `start_scanning()`.**
   - `start_scanning()` is part of the connection state machine: it sets `WIFI_COMPONENT_STATE_STA_SCANNING`, and when
     the scan ends ESPHome picks a network and connects again (`wifi_component.cpp:1455-1460`). Calling it while
     connected would drop the connection.
   - ESPHome itself scans while connected for its post-connect roaming (on by default, `post_connect_roaming`, every
     5 minutes when the signal is weak): `esp_wifi_scan_start()` with `coex_background_scan`, which returns to the home
     channel between the channels it scans, so the connection holds (`wifi_component_esp_idf.cpp:1068-1110`).
   - Its `WIFI_EVENT_SCAN_DONE` handler fills `scan_result_` whatever started the scan
     (`wifi_component_esp_idf.cpp:910-990`); the state machine only acts on results in its own scanning state, and the
     roaming code only on a scan it started (`is_roaming_scan_active()`, `wifi_component.cpp:883-886`). A roaming check
     that finds a scan already running backs off (`wifi_component.cpp:2600-2604`), and ours answers "busy" the same way.
   - Two conditions: while connected ESPHome keeps only results matching its own network unless a component calls
     `request_wifi_scan_results()` at code generation (`keep_scan_results_`); and a reader outside the main loop (the
     web server's task) must call `request_wifi_scan_results_lock()` and hold `ScanResultsLock`, as the portal does.
   - So M4 starts `esp_wifi_scan_start()` itself, background-coexistent and active, while connected and on the access
     point alike, and reads ESPHome's `get_scan_result()` under the lock. The Configuration page gets the dropdown too.
4. **Flash:** not measured yet (no build changes in M0). Expected small (one route, one NVS erase, a short JSON
   answer); M3 and M4 measure it. (M1 measured the starting point: the full build at 88.7%, 1,628,155 bytes. The plan
   first said 71.4%: that figure was firmware 1.0.1's, misread from docs/BENCH.md.)

### M1 Protected settings read-only over MQTT (D28, item 24)

- `FeederMqtt` (`feeder_mqtt.*`): `policy/{daily_cap,min_gap_s,portion_gap_s,max_portions_cmd}` keep publishing their
  retained state; `/set` on them is refused with `NOT_ALLOWED` and the value in force, whatever was set before.
- **MQTT Can Change Guard Limits** goes: the entity (`packages/mqtt.yaml`), its protected-list entry, the web app's
  switch on the MQTT card. Its Device flag `DEVICE_MQTT_GUARD` is retired: the bit is cleared on load (unknown bits
  already are) and stays reserved, so no record layout changes.
- `tests/test_mqtt.cpp`: every `policy/*/set` refused in every state; the schedule and one-shot topics unchanged.
- Docs: DESIGN.md section 9.6 and the scopes table (section 10.1), docs/MQTT.md, docs/SECURITY.md; D28 logged as
  reversing D24; item 24 closed.

### M2 Clear the BLE key (D29)

- Core: `clear_ble_key()` (all zero on the device: back to the build's key, or none), saved at once; the key serial
  changes, so a connected client's session ends (as on a key change today). Host test: before and after, YAML key and
  no key, AUTH refused with no key.
- Adapter: `/feeder/keys/ble` with no key clears, signed with the settings password, as `/feeder/keys/api` does.
- Web app: Clear beside Set and Generate on the BLE key (Configuration, Keys), with a confirm that says BLE clients
  stop working until a new key is set. Shown only when a key is saved on the device.

### M3 Forget Wi-Fi (D30)

- Build flag from code generation: the `wifi:` block has no network (the prebuilt binaries, which `!remove` theirs).
  Without it, nothing is compiled in and the web app shows nothing.
- Adapter: `POST /feeder/network/forget` (beside the other network endpoints), signed with the settings password, waits until the tray is not moving (as
  Restart does), does what M0 found, and restarts into the setup access point.
- Web app: Forget network under Configuration, Wi-Fi, with a confirm naming the access point (`<name>-setup`) and
  saying how to reach it again (join it, then the web app opens at its address). Offered whenever a network is saved,
  also from the access point, where it is harmless (it restarts into the same access point).
- The settings, calibration, keys and tray state are untouched: only the network goes.
- Done 2026-10-22: the full build is 88.8% (1,629,591 bytes, +1,060), basic compiles without it (no warnings in our
  code); the button and its confirm checked against the mock device. Not yet on hardware (M6).

### M4 Wi-Fi scan (D31)

- Firmware, as M0 allows: on the setup access point, the scan results the captive portal already has; while
  connected, a scan on request if it is safe, else none.
- `GET /feeder/wifi/networks`: name, signal, secured or not, strongest first, the same network once; not protected (the
  captive portal shows the same to anyone on the access point).
- Web app, Configuration's Wi-Fi and the setup wizard: a dropdown of the networks found, with Scan again and "Other
  network..." for typing a hidden one; a secured network asks for its password, an open one does not. Where scanning
  is not possible the typed name is all there is, as today.
- `tools/mock_device.py` serves a few networks, so the dropdown can be built and checked without hardware.
- Done 2026-10-22: `POST /feeder/wifi/scan` and `GET /feeder/wifi/networks` (DESIGN.md section 9.3). Full build 89.0%
  (1,633,539 bytes, +3,948: ESPHome now keeps its scan results), basic 61.4%; no warnings in our code. The web app is
  127 bytes under its 66 KB budget. Checked against the mock (list, Scan again, open and secured networks, "Other
  network...", the join sending the name as hex, and the typed-only dialog without the route). Not yet on hardware:
  M6 checks the link holds through a scan (bench step 4).

## Risks

| Risk | Mitigation |
|---|---|
| Forgetting the network leaves a feeder nobody can reach | Only in builds whose recovery is the setup access point and Improv (D30); the confirm names the access point; M0 checks it comes back exactly as after a fresh flash; bench item 3 |
| A scan while connected drops the connection | M0 decides; fall back to scanning on the access point only (D31) |
| Owners who used MQTT to change guard limits lose it | The release notes say so; the web app (and BLE, with its permission) still change them |
