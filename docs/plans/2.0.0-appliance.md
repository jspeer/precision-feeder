# Plan: firmware 2.0.0, "Appliance"

Status: **in progress**: N0 done except two bench checks (2026-10-15). Written 2026-10-15. Builds on 1.1.0
([1.1.0-local-first.md](1.1.0-local-first.md)), which must land first. The decisions
are logged in [DESIGN.md](../../DESIGN.md) section 13 and the checks still to make
are in section 14. When a milestone lands, DESIGN.md, AGENTS.md, the guides and
CHANGELOG.md are updated in the same change.

Part of the Precision Feeder ESPHome firmware (public domain, The Unlicense).
Designed and written with the assistance of an AI (Anthropic's Claude); reviewed by
a human, but it may still contain mistakes.

## Premise

Turn the feeder from "a firmware you build" into "an appliance you flash and set up
in a browser", as WLED does:
- Prebuilt binaries from GitHub.
- Install from a web page.
- A setup wizard.
- Settings changed at runtime.
- Update checks in the browser; the feeder itself never contacts the internet for updates.

ESPHome configures almost everything at build time, so most of this is one change:
**the personal settings move from the YAML into a settings record on the device.**
Those settings are pins, Wi-Fi, keys, timezone and hostname. This is a major version
because it reworks how the firmware is configured, installed and updated.

YAML builds stay supported as the advanced path. Their values become the starting
defaults, and saved settings win, as the servo pulse range already works today.

## Decisions (owner, 2026-10-15)

| Area | Decision |
|---|---|
| Binaries | Built by GitHub Actions: **full** and **no-BLE**, each as a factory image (first flash) and an OTA image. Diagnostics is in both |
| Target | Generic ESP32-S3, 4 MB flash, no PSRAM required |
| Flash | If the BLE build does not fit 4 MB, trim first; if it still does not fit, add an 8 MB BLE variant. A 4 MB image also runs on larger flash. The README gets a binary and flash matrix from measured sizes |
| Runtime settings | GPIO pins (servo, button, LED), Wi-Fi, hostname, timezone, API key, BLE key |
| API key | Kept in flash (NVS), not in the binary, using ESPHome's own provisioning (below) |
| Updates | WLED-style, done by the **browser**, not the feeder. On the Firmware page, the browser fetches `manifest.json` from GitHub Pages and compares it with the device's `Firmware Version` and `Firmware Variant`. Three outcomes, none blocking: up to date; update available (release notes and a link to the releases page); check failed ("Couldn't check for updates", with the link anyway). The user downloads the image and uploads it on the Firmware page, behind the settings password; the browser checks its SHA-256 against the manifest first. The check runs only when the Firmware page opens, and can be turned off (a browser setting). A feeder whose internet access is blocked loses nothing |
| Networks | As 1.1.0: dual-stack target with full IPv6 readiness. GitHub Pages has IPv6 but github.com is IPv4-only (N0), so on an IPv6-only network the update check works and only downloading the image fails |
| Web auth | Not required. A settings password, none by default, protects the sensitive settings instead |
| Protected settings | Wi-Fi and hostname; pins and board; API and BLE keys; the password itself; firmware update and upload; factory reset; **guard limits**; **calibration** |
| Never protected | Schedule, feeding, hold, tray reload, location, status: the device's purpose |
| Password recovery | Hold BOOT for 10 s after startup: clears the settings password only |
| BLE and the password | The BLE key and the API key are admin credentials. BLE keeps its current access to guard limits and calibration, because every BLE write is already authenticated |
| BLE toggles | Two protected settings, both default on: "BLE can change guard limits" and "BLE can change calibration" |
| Blank BLE key | AUTH always refused, so every write is refused. Never an all-zero key, which anyone could compute with |
| BLE refusals | `RES_NOT_AUTHORIZED` with new detail values 6 (no key set) and 7 (this setting is turned off for BLE) |
| BLE protocol | Stays 2: no packet layout or opcode changes, and 1.x clients do not break (the Python client prints unknown detail values; it authenticates once and does not retry refusals). PROTOCOL.md gains the rule that clients must accept unknown detail values |
| YAML builds | Kept as the advanced path |

## Logged decisions this reverses (each needs its DESIGN.md and AGENTS.md update when built)

- "OTA authenticates with the API key; no OTA password; **no web-server OTA**": 2.0
  adds upload in the browser, protected by the settings password. The feeder makes
  no update requests of its own (no HTTPS client on the device).
- "Every pin is a substitution with a documented default" (AGENTS.md): the
  substitution becomes the default; the saved pin wins.
- Timezone at build time only (section 6): 2.0 needs our own POSIX TZ parser.
- `!secret` API key in the YAML: the bins ship with no key and are provisioned on
  the device.

## Facts checked in the ESPHome 2026.9.1 source

- `api: encryption: {}` with no `key:` boots unprovisioned; the key is then saved
  in flash (its own preference slot, NVS on ESP32) and plaintext connections stop.
  Home Assistant can set it on adoption.
- `APIServer::save_noise_psk(psk, make_active)` saves a key. With
  `make_active = true` it takes effect after about 100 ms and drops connected
  clients, with no reboot. `clear_noise_psk()` returns to unprovisioned. So our
  own code can generate and set the key.
- Until a key is set the API accepts Noise with the all-zero key and, deprecated,
  plaintext, so Home Assistant can provision the key on adoption. That is the
  intended path (owner, 2026-10-15). A key sent over plaintext is deprecated, due
  for removal in ESPHome 2027.2.0; the all-zero Noise path stays (N0).
- OTA has a `USE_OTA_ENCRYPTION_PROVISIONED` path, so encrypted OTA uses the
  stored key. It can only offer encryption, not require it (N0: see N4).
- Avoid the optional `provisioning:` component: when its window closes it shuts
  down the fallback access point and captive portal.
- `web_server_base`: `add_handler()` applies web auth, `add_handler_without_auth()`
  skips it. The auth setters are public and take `const char*`, so web auth
  credentials could change at runtime, but web auth itself is compiled in or not.
- The captive portal is registered without auth and accepts `/wifisave` from
  anyone who reaches it. On the fallback access point, the access-point password
  is the only protection.

## Security model

- **No settings password set:** anyone on the network can change protected
  settings, as with WLED.
- **Password set:** protected changes need it. Home Assistant (API key) and BLE
  (BLE key) stay trusted through their own keys.
- **Physical access is the final trust boundary:** the BOOT button clears the
  password, and USB reflashes the board.
- **The password never crosses plain HTTP:**
  - The device sends a nonce; the browser answers with HMAC-SHA256, reusing
    `crypto.h` on the device.
  - The browser needs a small SHA-256 of its own, because `crypto.subtle` only
    exists on HTTPS pages.
  - The device stores a salted hash, and waits after each failed attempt, as BLE
    does.
- **Protected settings are not ESPHome entities that the REST interface can
  write:**
  - Preferred: exclude those entities from the web server only, if ESPHome
    supports that (N0 check).
  - Otherwise: show them as read-only entities, with Home Assistant changing them
    through `api: actions:`, which the web REST interface does not expose.
- **The fallback access point needs a documented default password in the bins.**
  The wizard prompts the user to change it.
- **The feeder makes no outbound connections** except NTP (and Home Assistant if
  used). Update checks run in the browser, so a firewalled feeder is fine.
- **The API key is trust on first use:** until Home Assistant (or the wizard)
  provisions it, anyone who reaches the device first can set it (N0).
- **Keys are stored in flash without flash encryption,** so anyone holding the
  board can read them. Documented.

## Flash outlook (estimates; N0 measures)

v1.0.1 uses 53% (about 0.97 MB, no BLE) and 71% (about 1.30 MB, BLE) of the
1.8 MB app slot. With update checks in the browser there is no HTTPS client or
certificate bundle on the device, so 2.0 adds roughly 120 to 180 KB:
- web app
- IPv6
- Improv
- upload in the browser
- runtime pins, timezone parser and settings password

Projected: no-BLE about 60 to 64%, BLE about 79 to 82%. Both should fit 4 MB.

Measured in N0 (2.0-shaped test build, ESPHome 2026.9.1): no-BLE 58.3%, BLE 76.3%,
against 57.5% and 75.7% for the 1.1.0 examples. About 430 KB remains in the BLE build
for 2.0's own code.

## Milestones

**N0, checks.**
- ESPHome:
  - `encryption: {}` with `save_noise_psk()` from our component, and OTA with
    the provisioned key.
  - Whether the captive portal is active only while the fallback access point is
    up.
  - Whether BLE can start at runtime, so it need not advertise until a key exists.
  - Whether ESPHome can exclude a single entity from the web server.
  - Improv serial with ESP Web Tools.
  - Runtime setup of the servo PWM, the LED driver and the button.
- Hardware and hosting:
  - Whether GPIO0 (BOOT) reads safely after startup on common S3 boards.
  - Whether GitHub Pages lets a browser read `manifest.json` from another site
    (CORS). If not, the Firmware page shows only the releases link.
  - Measure the flash budget of both variants.
- **Done 2026-10-15, except two bench checks** (GPIO0 after startup, and Improv with
  ESP Web Tools on a board). Answers in DESIGN.md section 14, item 10. Findings that
  change later milestones:
  - N2: ESPHome cannot hide one entity from the web server only; use the
    `api: actions:` fallback or a handler of ours registered before `web_server`'s.
  - N4: with a runtime key OTA accepts plaintext, so our component sets a random
    OTA password at runtime (`ota: password: ""`); Noise clients are unaffected.
  - N7: ESPHome's `/update` upload is guarded only by web auth, so the Firmware page
    uploads through a handler of ours on ESPHome's OTA backend.

**N1, device settings.**
- A new saved record "Device" with its own preference key and version.
  YAML values are the starting defaults.
- A POSIX TZ parser in plain C++, host-tested, so the timezone can change at
  runtime.

**N2, settings password.**
- The protected categories and the challenge and response, with delays after
  failures.
- BOOT-hold recovery.
- Protected settings moved out of REST-writable entities.

**N3, runtime hardware.**
- Servo, button and LED pins from settings, with "none" allowed for the button
  and the LED (everything still works with no button).
- A pin validator for the ESP32-S3: no flash, PSRAM or strapping pins, and a
  warning for octal-PSRAM boards.
- Board presets (Waveshare ESP32-S3-Zero, ESP32-S3-DevKitC-1, custom).
- A reboot applies pin changes.

**N4, keys.**
- API key in flash, with Generate and Clear.
- BLE key in flash, with Generate. A blank key refuses AUTH.
- Each key is shown once.
- The two BLE toggles and detail values 6 and 7, with tests in
  `tests/test_ble_engine.cpp`, the Python client and PROTOCOL.md.

**N5, network.**
- Wi-Fi and hostname settings.
- MAC-suffixed names in the bins, so two feeders do not collide.
- Improv serial.
- The fallback access-point password.

**N6, setup wizard.**
- First boot with no Device record: Wi-Fi, name, timezone and location, board and
  pins, keys, an optional settings password, then calibration.

**N7, distribution.**
- GitHub Actions builds the matrix, with manifests and images on GitHub Pages.
- An ESP Web Tools install page.
- A static `Firmware Variant` text entity (full or no-BLE), set at build time.
- `manifest.json` per release: version, release notes link, and each variant's
  image name and SHA-256.
- The Firmware page: the check in the browser, the three outcomes, upload behind
  the settings password, SHA-256 checked before upload.

**N8, hardening and bench test** (flashing only with the owner's go-ahead).
- A fresh flash from the install page.
- An upgrade from a 1.1 YAML build that keeps its settings and calibration.
- IPv4-only, dual-stack and IPv6-only networks.
- The update check with the feeder's and the browser's internet blocked.
- Results in docs/BENCH.md.

**N9, docs and release.**
- Installer guide, the security model, recovery, and the binary and flash matrix.
- DESIGN.md and AGENTS.md updated for the reversed decisions.
- CHANGELOG.md; tag 2.0.0.
