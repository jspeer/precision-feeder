# Plan: firmware 1.1.0, "Local first"

Status: **in progress**: M0 to M8 done (2026-10-15). Plan written 2026-10-15. The decisions are logged in
[DESIGN.md](../../DESIGN.md) section 13 and the checks still to make are in section 14.
When a milestone lands, DESIGN.md, the guides and CHANGELOG.md are updated in the
same change, and this file records the progress.

Part of the Precision Feeder ESPHome firmware (public domain, The Unlicense).
Designed and written with the assistance of an AI (Anthropic's Claude); reviewed by
a human, but it may still contain mistakes.

## Premise

The feeder must be fully usable as a standalone appliance: no Home Assistant, no
internet, no phone app. A browser on the same network, on a desktop or a phone, is
enough. Home Assistant and BLE stay optional add-ons.

Today that is not true: the stock ESPHome web UI loads its JavaScript from
`oi.esphome.io`, so with no internet there is no usable UI.

Constraints:
- Treat the existing, tested firmware as stable. The existing entities are the
  frontend's API: prefer adapting the frontend to the firmware. Firmware changes are
  allowed where the UI cannot work without them, and are read-only where possible.
- Every feed still goes through the one feed guard. The UI only requests; it never
  pre-decides a guard outcome or repeats scheduler or guard logic.
- Zero external runtime dependencies. The app is embedded in the firmware.
- The UI adapts to the features compiled into the device, by the entities present.

## Decisions (owner, 2026-10-15)

| Area | Decision |
|---|---|
| Stock ESPHome UI | Replaced. `packages/web_server.yaml` becomes the app. An "All entities" page is the debug fallback |
| Hosting | `web_server` version 3, `local: false`, `js_url: ""`, `css_url: ""`, `js_include` and `css_include` |
| Source | Plain JavaScript and CSS in `web/src/`, joined into `web/dist/` by a stdlib Python script (`tools/build_web.py`). `web/dist/` is committed so users need no tools; `tools/check.sh` fails if it is out of date |
| Tabs | Shown only when the entities a tab needs exist. No UI configuration file |
| Theme | Light and dark, following the browser's setting |
| Phones | First-class: bottom tab bar on narrow screens. A web UI, no native app |
| Web auth | Off by default. The `auth:` block stays in the package, commented, with its warning |
| BLE activity | A ring buffer in the BLE engine, served as JSON through `add_handler()` (so web auth applies when it is on) |
| Read-only additions | A, C, D, E and F below are approved |
| Profile names | Deferred (changes the saved Settings layout; needs a migration) |
| Runtime timezone | Not in 1.1.0 (DESIGN.md section 6) |
| Networks | Dual-stack is the target, with full IPv6 readiness: on an IPv6-only network everything local works (web UI, Home Assistant API, mDNS, NTP through IPv6-capable servers). Only services hosted elsewhere, such as GitHub (whose repositories are IPv4-only), may fail, and they fail gracefully. IPv4-only networks keep working |
| BLE protocol | No packet change; stays protocol 2 |

## Facts checked in the ESPHome 2026.9.1 source

- With `js_include`, the index page is `<link rel=stylesheet href=/0.css>`,
  `<script type=module src=/0.js>` and `<esp-app></esp-app>`. An empty `js_url`
  drops the stock app. The included files are gzipped into flash.
- `/events` (server-sent events) sends every entity on connect with full detail
  (`name`, `domain`, `min_value`, `max_value`, `step`, `uom`, select `option`,
  text `max_length`, `entity_category`), then state changes, `log` lines, and a
  `ping` carrying `title` and `uptime`. Writes are `POST /<domain>/<Name>/<action>`.
  Entities are addressed by their YAML name, so **entity names are the UI contract**.
- `web_server_base`: `add_handler()` applies web auth; `add_handler_without_auth()`
  skips it.
- Web auth defaults to `basic`, changing to `digest` in ESPHome 2027.1.0.

## Pages

| Tab | Shown when this entity exists | Content |
|---|---|---|
| Dashboard | `Tray State` | Tray dial, portions remaining, next feed and its portions, runway and empty-on date, Feed now with the guard state and a result toast, today's feeds, status, recent feeds, hold and resume, Tray reload walkthrough, position recovery |
| Schedule | `Edit Profile` | A/B/C viewer (viewing never activates), Make active, Scheduler switch, cadence and fast days, four event cards, the event dialog, one-shot feeds in device time |
| Configuration | `Daily Portion Cap` | Feeding safety, tray and refills, location and time (timezone read-only), device and network |
| Maintenance | `Calibration Mode` or `Declare Tray Position` | Calibration walkthrough, servo pulse range, declare position, Portions Counted (24 h) behind a warning |
| Bluetooth | `BLE Session` | Status, client, protocol counters, activity from the ring buffer |
| Diagnostics | always | System, memory (with the diagnostics package), live log, all entities |

Banners, one at a time, most severe first: connection lost; tray position unknown;
calibration mode on; tray empty; clock not set; next feed needs more than remains;
scheduled feeding on hold.

Rules for the UI:
- Field limits, steps and units come from the entity, never from a copy in the UI.
- The event dialog keeps a local draft until Save, then writes in the order
  docs/SCHEDULING.md gives (set the editor cursor and wait for its echo; anchor;
  time, days, portions; enabled last) and checks every value echoed back.
- Writes go one at a time.
- Device text is parsed tolerantly; if parsing fails, the raw text is shown.

## Read-only firmware additions

| | Addition | Why |
|---|---|---|
| A | `Schedule Data`: all 12 events plus cadence and fast days, compact | The Schedule page without stepping the editor cursor that Home Assistant shares |
| B | `BLE Info` (static) and `BLE Session` (connected, authenticated, masked peer address, connect and last-activity uptime, counters); diagnostic and disabled by default | The Bluetooth page |
| C | `Device Time`, with UTC offset | The timezone shown read-only; one-shot entry in device time |
| D | `Today`: today's resolved events with portions and fed / next / skipped / fast day | The Dashboard's today list and next-feed portions, without repeating scheduler logic |
| E | `Feed Guard`: a side-effect-free dry run of the guard for one manual portion ("ready", or the reason it would refuse) | Feed now explains itself, without repeating guard logic |
| F | ESPHome's own `wifi_info` and `wifi_signal` sensors | Network details in Configuration and Diagnostics |

Each text stays under 255 characters (Home Assistant's limit) and publishes through
the existing 1-second, publish-on-change pattern.

- Add `tools/mock_device.py`, a stdlib fake device with the same `/events` stream and
  POST endpoints, so the UI can be built and checked without hardware.
- Done when every check has a written answer, with a fallback agreed for any "no".
- **Done 2026-10-15.** Answers in DESIGN.md section 14, item 7. One "no": ESPHome's Wi-Fi
  needs an IPv4 address to count as connected (see M8). `tools/mock_device.py` serves the
  current entities, and `tests/test_consistency.py` checks its names against the packages.

**M1, read-only feeder data.**
- A, C, D and E in FeederCore, with host tests in `tests/test_core.cpp`.
- F in a package.
- Entity names checked by `tests/test_consistency.py`.
- `fw_version` 1.1.0; CHANGELOG.md gets an in-progress 1.1.0 section.
- **Done 2026-10-15.** Entities `Today's Feeds`, `Feed Guard`, `Device Time` (status.yaml) and
  `Schedule Data` (schedule_editor.yaml); formats in DESIGN.md section 7. F is the new optional
  `packages/network_info.yaml`, on in both examples. The mock device serves all of them.

**M2, BLE diagnostics.**
- Engine: connect and last-activity times, counters (writes in, notifications out,
  bytes, authentication failures, refused and invalid writes), opcode names in log
  lines, a ring buffer of about 32 entries with increasing ids.
- Adapter: masked peer address and MTU through a GATT server event handler, and reads
  counted through `on_read` (M0 found all three possible).
- The JSON endpoint runs on the HTTP server's task, so the ring buffer is read under a lock.
- Entities B; the ring buffer's JSON endpoint, built only when both the web and BLE
  packages are present.
- "Clear log" is client-side only (it remembers the last id), so no new write exists.
- Tests in `tests/test_ble_engine.cpp`; a PROTOCOL.md note that nothing on the air
  changes.
- **Done 2026-10-15.** Endpoint at `GET /feeder/ble`. The engine owns the counters and the
  ring; the adapter feeds it the peer address and MTU (GATT server events) and reads (`on_read`),
  and rebuilds the JSON on the main loop only when the log changes. Formats in DESIGN.md
  section 7. The mock device serves both entities and the endpoint.

**M3, web app foundation.**
- The package swap, `web/src/`, `tools/build_web.py`, `web/dist/`, the check.sh step.
- Entity store, a write queue that waits for the device's echo, tab and section
  detection, shell (top tabs on desktop, bottom bar on phones), theme, banners,
  toasts, Diagnostics and All entities.
- `test_consistency.py` checks every entity name used in `web/src/` exists in a package.
- Done when it works against the mock device, an empty build shows only Diagnostics,
  and the app stays within about 60 KB gzipped.
- **Done 2026-10-15.** 18 KB gzipped. Checked in a browser against the mock: desktop and phone
  layouts, light and dark, banners (position unknown, connection lost), the Tray Reload walkthrough,
  writes confirmed by the echo, range checks from the entity, basic auth. Found and fixed on the way:
  - ESPHome's index page has no viewport tag, so the app adds one; without it phones render 980 px wide.
  - A page opened as http://user:pass@host/ makes relative fetch() URLs carry the credentials, which
    browsers refuse, so writes go to `location.origin`.
  - Only Diagnostics has a page so far, so it is the only tab.

**M4, Dashboard. M5, Schedule. M6, Configuration and Maintenance. M7, Bluetooth.**
As in the Pages table.
- **M4 done 2026-10-15.** Next feed portions come from Today's Feeds when the next feed is today; for a
  later day only the time is shown (the next feed's portions are not exposed on their own).
  - Feed now asks for confirmation, then reports the device's answer: a new Recent Feeds entry, or Last
    Result. A refusal repeated unchanged causes no update, so after 3.5 s the current Last Result is shown.
  - Position recovery runs from the banner whenever the calibration package provides Declared Tray Position.
- **M5 done 2026-10-15.**
  - Viewing a profile reads Schedule Data and never touches Edit Profile or Edit Event; they are set only to
    save.
  - Event saves: a live event is turned off first if its timing changes; then anchor, time, days and
    portions; Enabled last. Each write is confirmed by its echo, and the result by Schedule Data.
  - Found with the mock and fixed:
    - waitForChange could miss an update that arrived before the request that caused it had returned, so it
      now checks the state first.
    - Dialogs resolved only on the dialog's "close" event, which a hidden browser tab can hold back; they
      now resolve on the submit (or Escape).
  - For M9: a tab left open across a firmware update keeps running the old app; prompt a reload when the
    Firmware Version changes.
- **M6 done 2026-10-15.** Configuration uses the entities' own controls. The time zone is shown read-only,
  as the UTC offset from Device Time. Maintenance drives calibration through Calibration Mode, Position and
  Offset (each nudge confirmed); the pulse range sits under "advanced", and the device refuses a pair less
  than 500 µs apart. The mock now models the 24 h count edit as the firmware does.
- **M7 done 2026-10-15.** The activity log is fetched when BLE Session's connection or write counters
  change, not on a timer. "Clear view" is per browser (local storage) and resets when the feeder's entry ids
  restart (a reboot). Checked without the BLE and calibration packages: Bluetooth disappears, `#bluetooth`
  falls back to the Dashboard, and Maintenance keeps tray reload and the 24 h count. With M7 every page
  exists, so the hardware test can start before M8.
- **First hardware test 2026-10-15** (after M7): every page works on a real board; details and what is still
  unchecked in docs/BENCH.md.
- **M8 done 2026-10-15**, and checked on hardware the same day on a dual-stack network (docs/BENCH.md):
  - `network: enable_ipv6` through the `enable_ipv6` substitution, with `min_ipv6_addr_count: 0`.
  - The ESPHome source shows the API and web server listening dual stack with IPv6 on.
  - The app makes only relative or `location.origin` requests, checked against the mock at
    `http://[::1]:8080/`.
  - Diagnostics labels each address.
  - The README documents the IPv6-only fallback (static IPv4) and an IPv6-capable NTP server.
  - Found on the way and fixed: a page opened directly by its address could mount before the entities
    arrived and miss parts of the build.

**M8, IPv6.**
- Turn on IPv6; relative URLs only in the app; mDNS over IPv6.
- NTP defaults reachable over IPv6 (or a documented NAT64 note), so the clock works on an
  IPv6-only network.
- The UI shows IPv6 addresses.
- M0 found that ESPHome 2026.9.1's Wi-Fi only counts as connected with an IPv4 address,
  so a network with no DHCPv4 needs a static IPv4 address (`manual_ip`) at least. Whether
  that is enough is checked in M10; the docs say what IPv6-only networks need.

- Keyboard use and screen-reader labels; phones at 360 px.
- Measure the heap cost of each open browser.
